# 阶段 2 设计:Docker 沙箱 + 变异式任务生成器

> 状态:沙箱与生成器已实现并通过测试,并已用于全部 M5 实验(种子库最终定为 14 个 PyPI 小库 + 2 个手写,352 题,见 `seeds/SOURCES.json` 与 `docs/next_phase_plan.md`);本文是设计时的记录,个别数字以后者为准。目标见 [next_phase_plan.md](next_phase_plan.md) 的阶段 2。写于 2026-10-18。

## 0. 要解决的两个问题

1. **安全**:agent 的 `bash` 和评测时跑的测试都在宿主机上直接执行模型生成的代码(README 的安全说明里写明了)。批量生成任务、批量采样轨迹、以后还要在租来的卡上跑学生模型,这些都会放大风险。
2. **数据**:训练需要几百个互不相同的可验证任务,而现有 39 题要留作评测,不能拿来训练。

## 1. 沙箱

### 1.1 范围(威胁模型)

要防的:模型写的命令或代码**读宿主文件、拿宿主环境变量里的 API key、联网外泄、把磁盘/内存/进程数耗尽、留下孤儿进程**。

不防的(如实写进局限):内核/容器运行时漏洞(逃逸需要 0-day)、通过挂载目录对工作区本身的任何操作(工作区本来就是 agent 可写的)、侧信道。容器共享宿主内核,强度低于虚拟机。

### 1.2 结构

只有两处会执行代码,所以沙箱只包这两处:`bash` 工具、评测判分时的测试。`read_file`/`write_file`/`edit_file`/`grep` 是宿主上的 Python 代码,只操作工作区目录(已有路径越界检查),不执行任何东西。

```
宿主                                   容器(每次运行一个,运行结束即删)
Workspace(root) ── bind mount ──▶  /work  (读写)
  bash 工具 ── docker exec ──▶  timeout -k 2 T bash -c "<命令>"
评测判分 ── 另一个新容器 ──▶  pytest …(工作区同一目录)
```

- **每个 agent 运行一个长驻容器**(`sleep infinity`,带 `--init` 回收僵尸进程),每条命令 `docker exec`,避免每条命令都付一次启动开销。判分用**另一个新容器**,避免 agent 留下的后台进程干扰判分。
- 容器参数(缺一项都有对应的逃逸测试):
  `--network none`、`--read-only`(根文件系统只读)、`--tmpfs /tmp`(可写、限大小)、`--cap-drop ALL`、`--security-opt no-new-privileges`、`--pids-limit`、`--memory`(含 swap 同值)、`--cpus`、`--user <宿主 uid:gid>`(非 root,工作区里新建的文件属主正确)、不传任何环境变量(拿不到 `DEEPSEEK_API_KEY`)、统一 label 便于清理孤儿。
- **超时**:容器内用 `timeout -k 2 T`(杀整个进程组);宿主侧再加一层兜底,超时就 `docker kill`。
- **清理**:`close()` 里 `docker rm -f`;`atexit` 再兜一次;`cleanup_orphans()` 按 label 清掉崩溃遗留的容器。
- **镜像**:`sandbox/Dockerfile`,基于 `python:3.12-slim`,固定版本安装 pytest(与宿主一致)。运行时断网,所以种子仓库只能依赖标准库 + pytest。
- **接入**:`Workspace(root, sandbox=None)`;给了 sandbox 才走容器,默认行为不变。评测配置加 `"sandbox": true`,CLI 加 `--sandbox`。沙箱内的路径统一是 `/work`(副作用:模型看到的路径长度固定,对回放的确定性反而有利)。
- 现有的命令黑名单保留(纵深防御),但不再被当作边界。

### 1.3 逃逸测试(`tests/test_sandbox.py`,没有 Docker 时自动跳过)

联网被拒;读不到宿主文件(包括工作区外放的"秘密文件");宿主环境变量里的 key 不可见;根文件系统写不了、`/tmp` 写得了;不是 root、`mount` 被拒(没有 capability);fork 炸弹被 pids 限制挡住且命令按时返回;内存超限被杀;超时后整个进程组被清掉;容器里创建指向 `/etc/passwd` 的符号链接,宿主侧 `read_file` 仍拒绝;输出洪水被截断;工作区里的改动在宿主可见且属主正确;`close()` 后容器确实消失。另有**不需要 Docker** 的单元测试检查生成的 `docker run` 参数里每个安全选项都在,并做变异检查(去掉一项,测试必须失败)。

## 2. 变异式任务生成器

### 2.1 思路

拿一个**能通过自带测试的种子库**,在它的源码里**注入一个小 bug**(变异),得到一道题:

- `repo/`:被注入 bug 的源码 + **可见测试**(种子测试的一个子集)
- `hidden/`:**完整**的种子测试(判分时覆盖可见测试)
- `solution/`:原始(未变异)源码
- 初始必须失败、参考解必须通过(沿用 `miniagent-eval verify`)

不用 API:变异、运行测试、筛选全部在本地沙箱里完成。

### 2.2 变异算子(基于 `ast` 定位、对源码文本做最小替换,不重排格式)

比较运算符翻转(`<`↔`<=`、`>`↔`>=`、`==`↔`!=`);算术运算符互换(`+`↔`-`、`*`↔`//` 等);布尔运算符互换(`and`↔`or`);条件取反(`if x` → `if not x`);整数常量 ±1;`break`↔`continue`;删除一条语句(赋值、增量赋值)。每个候选只改一处,替换前核对该处源码确实是预期的运算符(括号、注释、续行里找不到就放弃这个候选)。

### 2.3 有效性筛选(每一条都是为了避免一类坏题)

| 检查 | 排除什么 |
|---|---|
| 变异后能编译 | 语法错误 |
| 原始代码通过全部测试(跑两次) | 种子本身有问题或有随机性 |
| **可见测试至少失败 1 个** | bug 在可见证据下完全不可发现 → 题目不公平(案例 10 的教训) |
| 完整测试失败数 ≤ 上限(默认 ≤ 8 且 ≤ 40%) | 一改就全崩(导入错误等),没有诊断价值 |
| 变异后的失败集合跑两次相同;无超时 | 不稳定、死循环 |
| 同一种子内,按"失败测试集合"去重,每组最多取 1~2 个 | 同一个 bug 的重复变体 |
| 变异的位置不在测试文件里 | 改到测试 |

### 2.4 可见/隐藏测试的划分

按测试函数拆分:把测试文件里随机一部分 `test_*` 函数(含类里的方法)从可见版本中删掉,保留 import、fixture 和辅助代码。划分用固定随机种子,可复现。要求:可见版本在**原始代码**上全过(否则删坏了),且在**变异代码**上至少失败 1 个(2.3 的第三条)。判分时 `hidden/` 里的完整文件覆盖可见文件,这套机制现有的 `restore_tests` / `add_hidden` 已经支持。

### 2.5 训练/评测隔离(防数据泄漏)

- 生成的任务放在单独的目录 `gen_tasks/`,**不进入** `tasks/`,不影响现有 dev/test 划分与已跑过的结果。
- **按种子库(仓库)划分**,不是按任务:同一个库的所有变异题同属一个划分。划分写入 `gen_tasks/SPLIT.json`:`train`(用来合成训练轨迹)、`dev`(未见库,开发时评测)、`test`(未见库,最终评测,沿用 `--final` 保护)。
- SFT 导出器默认**只导出 `train`**;导出其他划分必须显式指定。
- 人工写的 39 题与全部既有结果仍然只属于评测。

### 2.6 局限(提前写明)

- 变异出的 bug 比真实 bug 机械,且种子库若是知名开源库,学生模型预训练时可能见过原始代码(评测可能被高估)。
- 可见测试里至少一个会失败,所以"没有规格、只能靠测试发现 bug"的难度类型没有覆盖;这与手写 B 层(规格驱动、假完成)是互补的,不是替代。
- 运行时断网,所以种子库只能依赖标准库和 pytest。

## 3. 需要你决定的一件事:种子库从哪来

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. PyPI 上小而纯 Python 的库**(推荐) | 从 PyPI 的 JSON 接口取源码包(sdist),只下载、解压,**不在宿主上执行任何东西**;测试只在沙箱里跑。生成器会自动剔除测试在原始代码上不过、或需要额外依赖的库 | 要联网下载几十个小压缩包(各几十到几百 KB),每个库的许可证需要核对 |
| B. CPython 的 `Lib/` + `Lib/test/` | 标准库本身,PSF 许可证,无外部依赖。你本机的 conda Python 已经把测试目录删掉了,需要下载 CPython 源码包(约 25 MB) | 测试依赖 `test.support`,需要写一层兼容垫片;模型预训练几乎一定见过 |
| C. 自己写种子 | 不下载,质量可控 | 工作量大,数量上不去 |

生成器本身不依赖选择:种子是一个目录(`src/` + `tests/` + `seed.json`),换来源只是换"怎么得到这个目录"。

## 4. 验收标准(阶段 2 出口检查)

- 沙箱:逃逸测试全过;变异检查证明每个安全选项都有测试守着。
- 在沙箱里重跑一批旧任务(A/B 层),结果与宿主上一致。
- 生成器:对随手写的 2 个小种子,生成的每道题都通过 `verify`;被筛掉的变异按原因计数。
- 真实种子:200+ 道通过 `verify` 的题,来自至少若干个不同的库,并给出各筛选原因的丢弃数量。
