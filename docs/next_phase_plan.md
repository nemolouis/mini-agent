# 下一阶段计划:从评测 harness 到"评测驱动的数据与训练闭环"

> 状态(2026-10-21):阶段 0~4 完成。第三次 LoRA 训练成功(前两次发散),学生模型在 dev 上从 0/48 到 4/48,**这个差距在统计上不显著(p≈0.12)**,但行为变化很明确(0 → 48 次运行都在用工具,8 次改了文件)。阶段 5 做了一半:前后对比做了,数据消融和 test 集没做;阶段 6(上下文工程,可选)未做。这是一次**主动改变范围**的决定:此前 [PROJECT.md](../PROJECT.md) 把模型训练列为"不做",本计划把它改为"做最小可验证的一条链路";PROJECT.md 与 README 的定位已同步修改。下面的阶段表是写计划时的估算,文末按时间顺序记录了每一步的实际结果,两者不一致时以后者为准。

## 一、目标与定位

现状:M1(agent)、M2(评测)、M3(回放)、M4(MCP)已完成,项目的价值在评测方法的严谨性,而不是技术难度。

目标:补上"下层"能力,形成一条完整链路——**可验证任务集 → 轨迹合成 → SFT → 用同一套 harness 评测前后差异**。同时补强三块工程深度:确定性回放、真沙箱、上下文工程。

**最低完成线**:阶段 0~5 全部完成。阶段 6 是加分项,可整体砍掉。

## 二、设计原则

1. **先做能省钱的**:确定性回放排最前,后面每一步都受益。
2. **沙箱与任务生成合并**:任务生成要批量执行不可信代码,Docker 环境本身就是沙箱,不分开做。
3. **先用不花钱的手段验证管线,再烧 API**:每个阶段有出口检查,不通过不往下走。
4. **上下文工程放最后且可砍**:最费 API,与主线最远。

依赖关系:

```
回放 ─┬─> 沙箱+任务生成 ─> 轨迹合成 ─> SFT ─> 评测+消融
      └─────────────────────────────────────────> 上下文工程(可选)
```

## 四、各阶段要点

### 阶段 1:确定性回放
- 录制粒度:一次模型请求 → 一次响应,以请求内容哈希为键。
- 用途:调试 loop、过滤器、导出器时零成本复现;相同请求不重复付费。
- 局限:回放只能验证"系统"的改动,不能预测新模型/新提示词的行为。

### 阶段 2:沙箱 + 任务生成
- **任务生成不用 API**:对种子仓库做 AST 变异(翻转比较符、off-by-one、删行、改常量),以仓库自带测试的一部分作隐藏测试。有效性校验沿用现有 `verify`。
- 局限需如实写明:变异出的 bug 不如真实 bug 自然。
- **划分按仓库或模板切**,不是按任务切,否则同一仓库的变体会同时出现在训练和评测里(数据泄漏)。
- 沙箱要有对应的逃逸测试:读宿主文件、fork 炸弹、联网外泄、写根文件系统。
- 沙箱完成后,README 里"bash 不受路径限制、在宿主机直接执行"的安全说明需要更新。

### 阶段 3:轨迹合成
- teacher 首选 DeepSeek flash(B 层约 90%,单次约 $0.006)。
- 先试点再放量;保持 system prompt 与工具定义稳定并置于最前,以利用前缀缓存折扣。
- 过滤:只留隐藏测试通过的轨迹;去重;去掉死循环与无效调用;统一格式。
- 需要先核实:现有 `trajectory.jsonl` 能否还原成训练用对话格式(是否缺思考内容、原始 tool_calls 格式等),并编写导出器。

### 阶段 4:SFT
- 先在小模型上调通数据格式与训练脚本,再租卡训练 7B,训练完立即关机。
- 学生模型用 vLLM 起 OpenAI 兼容服务,客户端不用改。

### 阶段 5:评测 + 消融
- 评测集必须是训练中**从未出现的仓库**。
- 风险:学生模型可能在原 B 层上接近 0%(地板效应)。应对:评测集增设一档较易的题,扩大题数,沿用配对对比与区间。
- 提升可能很小甚至为零,如实报告;分析扎实本身就有价值。

### 阶段 6:上下文工程(可选,收缩版)
- 原料:阶段 1~3 已录制的长轨迹(免费)。
- 方法:对同一段历史用不同压缩方法各生成一次结果。
- 指标:规则化的信息保留度(是否保留已改文件、失败测试、已排除假设),不再调用判官模型。
- 只对最后挑出的一两种方法,在 `g35-mid` 子集上用免费额度做一次真实对比。

## 五、API 额度紧张时的对策

1. 任务生成与有效性校验完全本地,不用 API。
2. 最值得花的一笔钱:给 DeepSeek 充约 $10。免费 Gemini 每天 500 请求,每次运行约 10~20 步,一天只能跑二三十次,500 条轨迹需两三周,且有思考签名、中转等麻烦。
3. 先试点 30 题,用真实通过率和单条成本决定放量规模。
4. 回放当缓存用,调试阶段不付费。
5. 学生模型的评测在自己租的卡上跑,不消耗 API。
6. 租卡先在小模型上调通管线,再开 7B,按小时计费,用完即关。

## 六、风险与砍线

| 风险 | 对策 |
|---|---|
| 变异任务有效率低(太容易或不可解) | 阶段 2 出口检查;不过就缩小种子仓库范围,宁要 100 个高质量任务 |
| teacher 在新任务上通过率低 | 试点阶段发现;降低难度或多采样 |
| 小模型学不会,评测接近 0% | 评测集分一档较易题;阶段 4 先用小模型暴露问题 |
| 评测题数太少 | 评测放在未见仓库的几十题上,如实报告区间 |
| 时间不够 | 砍线顺序:先砍阶段 6,再砍阶段 5 的消融(只留"训练前 vs 后"),最后才动主线 |

## 七、边界(不要这样写简历)

- 不写"完整 MCP 协议实现",MCP 尚未与官方 SDK 做互操作验证。

## 阶段 4 准备与训练前基线(2026-10-19)

环境:`.venv-mlx`(Python venv,mlx 0.32.4、mlx-lm 0.32.2、transformers 5.20.1,共 461 MB);学生模型 `Qwen/Qwen2.5-Coder-1.5B-Instruct`(Apache-2.0,3.1 GB,提交 2e1fd397ee)放在 `models/`。训练脚本 `scripts/sft_mlx.py`(自写,见下)。

- **为什么不用 `mlx_lm.lora`**:它只有一个"提示长度"偏移量,多轮轨迹里的工具输出(文件内容、测试输出)也会被当作要预测的目标。`sft_mlx.py` 只对助手轮(工具调用、文字和结尾的 `<|im_end|>`)算 loss;`check` 命令验证过掩码:510 条样本每条的掩码段数都等于助手消息数;有 loss 的 token 只占 9.1%(约 34 万)。
- **长度**:真实 token 数共 371 万,中位 6.2k,p90 13.1k,最大 32k。≤8192 的有 330 条(65%),≤12288 有 437 条(86%)。训练最初用 `--max-len 8192`,更长的样本整条丢弃(不截断),训练集 313 条(另有 17 条验证),**偏向短而简单的题**。(后来因显存问题改为 `--max-len 4096`,训练集只剩 152 条,见文末。)
- **内存**:词表 15 万,完整 logits 在 8k 长度下约 5 GB。只在有 loss 的位置(最多 2048 个/条)计算输出层,与完整计算的损失差 ≤ 2.4e-7(5 条样本核对);峰值内存约 8.9 GB。
- **MLX 的一个坑**:`(ce * weights).sum() / weights.sum()` 且同一个和又被返回时,MLX 0.32 的编译梯度步报 `unordered_map::at: key not found`,逐项二分后改用 `where` 加两个独立的计数。
- **速度**:稳态约 25~35 秒/条(≤8k)。1 个 epoch 约 3 小时,2 个 epoch 约 6 小时。48 条冒烟训练中,训练损失 1.87→0.98,验证损失 1.85→1.02(验证只用 2 个样本,很粗)。
- **服务**:`mlx_lm.server` 用请求里的 `model` 字段选模型,只有 `default_model` 指向启动时加载的模型和适配器;写成别的名字会去 Hugging Face 下载。服务端只在模型输出 `<tool_call>` 标签时才返回结构化 `tool_calls`。

**训练前基线**(`results/20261019-174449-student-base-qwen15`,dev 划分 48 题、未见过的库 colorama 和 schema):**0 / 48**,48 次全是 `no_edit`,每次 1 步。基础模型没有调用工具,而是输出 JSON 代码块或计划文字。这个 0% 反映的是"不会用 `<tool_call>` 格式",不是代码修复能力;训练前后的对比因此会有"格式学会了"和"真的会修"两个混在一起的因素,需要单独看失败类别。

## 阶段 4 训练记录(2026-10-19 至 10-20):两次发散,第 60 步检查点不会调用工具

| 运行 | 配置 | 结果 |
|---|---|---|
| `qwen15-v1`(bf16,全部 28 层,≤8192 token,lr 1e-4,无裁剪、无守卫) | 训练损失 1.17 → 2.35(第 40 步)→ 10.9(第 104 步);验证损失 1.81 → 2.67(第 77 步)→ 6.88 | **发散**,5.5 小时后才被人发现,检查点全部作废 |
| `qwen15q4-v2`(4 位基础权重 QLoRA,最后 16 层,≤4096 token,lr 5e-5 + 预热,裁剪 1.0,守卫) | 损失 1.89 → 0.95(第 64 步),验证 2.10 → 0.938(第 59 步);第 80 步 1.56,第 88 步 4.33 | **再次发散**,守卫在第 88 步自动停止(约 1 小时) |

**过程中的事故**:调试显存时我连续把 Metal 显存顶到上限,出现 `kIOGPUCommandBufferCallbackErrorOutOfMemory`,之后整机内核崩溃(`completeMemory() prepare count underflow @IOGPUMemory.cpp:550`,2026-10-20 01:24)。我判断是我的操作触发的,但无法排除 macOS 26.1 驱动缺陷。此后:MLX 自身内存上限 7 GB(训练)/ 4 GB(服务)、先做 `memtest` 再训练、4 位基础权重。

**两条已经发现的原因线索**:
1. 对全部 28 层加 LoRA 时,第 0 层 q/k/v 的 LoRA 梯度范数达 1e13~1e16,其余层约为 1(梯度检查测得)。改为只训练最后 16 层,同时降低了显存。
2. MLX 的 `AdamW` 默认**不做偏差修正**,前 100 次更新的实际步长是名义学习率的 3.2~6.5 倍(已用数值验证)。第一次在第 10 次更新、第二次在第 19 次更新发散,都落在这个窗口里。这是与数据吻合的推断,**还没有用"打开修正后不再发散"的重跑来证实**。

**第 60 步检查点的端到端评测**(dev 划分,48 题,同一套 harness,4 位基础模型):

| | 通过 | 失败类别 | 工具调用 |
|---|---|---|---|
| 基础 4 位模型(`results/20261020-120914-student-q4-base`) | 0 / 48 | `no_edit` × 48(输出计划文字后正常结束) | 0 |
| 第 60 步适配器(`results/20261020-120914-student-q4-step60`) | 0 / 48 | `max_tokens` × 48(重复 "I'll start by exploring the repository structure." 到 1024 token 上限) | 0 |

进程内核对(绕开服务端)得到同样的行为,所以不是服务端设置的问题:对训练样本助手 token 的逐词预测准确率 0.687(基础)→ 0.811(第 60 步),但"第一句话之后接 `\n<tool_call>`"这个决定还没学会,模型选了 `\n\n`。第 60 步只做了 15 次参数更新。

**结论**:目前**没有任何训练后的模型能完成哪怕一次工具调用**,所以训练后对比不成立,README 里的"闭环"只完成了数据一半。下一步是用打开偏差修正的配置重跑,先看能否越过第 20 次更新而不发散。

## 阶段 4 第三次训练与第一次前后对比(2026-10-21)

**训练**(`adapters/qwen15q4-v3`):4 位量化基础权重,只训练最后 16 层,max-len 4096(152 条训练、7 条验证),**打开 Adam 偏差修正**,峰值学习率 1e-4(10 次更新预热),梯度裁剪 1.0,守卫开启,MLX 内存上限 7 GB。456 个样本步(114 次更新)全部跑完,105 分钟,峰值显存 5.5 GB,**没有发散**。训练损失 1.93 → 0.43;验证损失 2.103 → 0.867(第 59 步)→ 0.753(第 119 步)→ 0.675(第 299 步,最低)→ 0.736(最终)。第二次在第 80~88 步发散的位置,这次的损失是 0.75、0.74。验证集只有 7 条,第 299 步之后的小幅回升只能算轻微过拟合的迹象。

**这次成功能说明什么**:和"MLX 的 AdamW 默认不做偏差修正,前 100 次更新步长被放大 3~6 倍"这个推断一致。**但它只是一次运行,而且同时改了好几样**(偏差修正、学习率 5e-5 → 1e-4;计划的步数和其他配置相同,第二次只是被守卫提前停了),没有做只改偏差修正的对照实验,所以因果仍是推断,不是证明。

**一个新的根因:工具调用标记 token 的嵌入没训练过**。第三次训练的模型把整个格式学会了(一句话 → 标记 → JSON → 标记 → 结束),但在应该输出 `<tool_call>`(151657)和 `</tool_call>`(151658)的位置输出的是 124 号 token(解码成 U+FFFD),服务端因此收不到工具调用。检查原始 bf16 权重:这两个 token 的嵌入行与 124 号行最大相差 6.1e-5(约一个 bf16 舍入单位),范数都是 0.391,是未训练的占位值;输出层与嵌入共享权重,LoRA 又不改它们,所以三者在输出端的得分几乎相等,贪心解码取到编号最小的 124。(`<|im_end|>`、`<|im_start|>` 的嵌入是正常训练过的。)这解释了第 60 步检查点为什么只会重复开头那句话,也解释了为什么前两个模型都从未输出过工具调用。

**修法**:客户端宽容地解析回复文本里的 JSON 工具调用(配置项 `text_tool_calls`,默认关闭;只接受提供的工具名;7 个测试,6 个变异检验)。这是对一个模型缺陷的绕过,不是正式的工具调用协议。训练前的基线用**同样的解析**重测,保证对比公平。

**评测**(dev 划分,48 题,colorama 和 schema 两个未见过的库,每题 1 次,温度 0,同一套 harness 与沙箱)。**检查点事先定好**:最终适配器是主要结果,验证损失最低的第 300 步是次要结果,两个都报告:

### edit_file 错误提示的配对实验(2026-10-25)

**改动**:`Workspace(edit_hints=True)`(配置项 `edit_hints`,默认关)。`old_string` 找不到时,返回文件里最相近的真实行(带行号,并说明是否只差缩进);多处匹配时给出行号;文件不存在时给出相近文件名。工具说明、提示词都不变,只有失败信息不同。新增 7 个测试(共 364 个,全过)。
**设计**:同一适配器(v3 最终)、同样 dev 48 题、温度 0、各跑 1 次;跑之前写下的预测是"通过数高于 4/48,`no_edit` 少于 34"。配置 `configs/student-q4-v3-final-hints.json`。
**结果(预测没有成立)**:通过 4/48 → 3/48(退步 1 题:g-colorama-017-arith,改进 0 题,其余 47 题不变);`no_edit` 34 → 39。edit_file 调用:84 次失败/10 次成功 → 90 失败/8 成功。差异在噪声之内,不能说提示有害,只能说没有帮助。
**原因(事后统计,只描述,没做对照)**:90 次失败里只有 11 次能给出有用提示(其余是"完全相同"或文件里根本没有相近文本)。更关键的是,失败之后模型的下一次 edit_file 调用与上一次**完全相同**:基线 56/59,加提示后 51/58。1.5B 学生基本不读失败信息再改,所以改反馈这一层没有杠杆。
**含义**:瓶颈在学生模型的行为(不先 read_file 就编造 `old_string`,失败后原样重复),不在工具反馈。更可能有用的方向是训练数据层面:只保留"先读后改"的轨迹,或加入"失败后修正"的样本;这是下一步的假设,没有验证。

### 重训 v4(缩短 old_string)的评测结果:无效,不能检验假设(2026-10-25)

**训练**:`adapters/qwen15q4-v4-shortedit`,数据 `sft_train_v3.jsonl`,超参与第三次一致(456 步,无发散,验证损失 2.11 → 0.752;验证集多 1 条,损失不可直接比)。
**评测**(dev 48 题,配置 `configs/student-q4-v4-shortedit-final.json`,其余与基线一致):**0/48**,48 题全是 `no_edit`,平均 1.0 步。基线 4/48,逐题对比退步 4 题、改进 0 题(McNemar 精确检验 p=0.125,不显著)。
**但这不是"缩短有害"的证据**:48 次运行都是模型说了一句"I'll start by exploring the repository structure."(10 个 token)就以 `<|im_end|>` 结束,**一次工具调用都没发出**,所以 edit_file 根本没有被用到,"凭空写 old_string 的比例"无从统计(预测里的这一项没法检验)。直接向服务发第一次请求并看 logprobs,结果一致:句末直接结束,备选 token 的概率都很低且几乎持平。

**结论**:这一轮没有回答"缩短 old_string 是否有用"。当前瓶颈先是工具调用的格式不稳定。

### 工具调用格式的方案(2026-10-25,只查看和离线验证,没改仓库、没训练)

**训练文本里到底是什么**:`sft_mlx.encode` 用模型自带的 `chat_template.jinja` 渲染。助手的工具调用被渲染成 `\n<tool_call>\n{"name": …, "arguments": …}\n</tool_call>`,其中 `<tool_call>`(151657)和 `</tool_call>`(151658)各是**一个特殊 token**,而且在助手回合内,所以损失要求模型自己生成它们。这两个 token 的嵌入没训练过(约等于 token 124),输出层又共享嵌入,所以它们的 logit 几乎相同,模型分不出"该发标记"和"该发 token 124",这就是前面看到的不稳定。数据里助手回合内的这类特殊 token 共 10184 个。
**方案 1(推荐):把助手要生成的工具调用改成普通文本**。模板里的 `<tool_call>…</tool_call>` 换成 `[TOOL_CALL]…[/TOOL_CALL]`(普通 token),系统提示里的说明同步改;工具返回仍用原来的 `<tool_response>`(只出现在输入里,不要求模型生成,不动它)。在临时目录做了原型并在 CPU 上验证:助手回合内的特殊 token(除 `<|im_end|>`)10184 → **0**;把 510 条的助手文本用 `extract_text_tool_calls` 解析回去,与原工具调用**510/510 完全一致**(第一次比较写错了,把字符串和字典比,得到 0/510,修正后重跑);长度变长,max-len 4096 内的样本 160 → 155 条(−5)。
**方案 2:给两个标记初始化不同的嵌入**。保留 Qwen 原生格式和服务端的结构化 tool_calls,但嵌入是 4 位量化且输出层共享,要改权重文件(重新量化这两行)并生成新的模型目录,初始化取什么也没有验证过;没做任何实验,风险更大,不推荐。
**方案 1 要改的文件**:
1. 新增 `prompts/chat_template_plain.jinja`(上面的原型,从模型自带模板改两处)。
2. `scripts/sft_mlx.py`:`encode` 接受并使用该模板(加 `--chat-template` 参数);`check`/`memtest`/`train` 都要带上。
3. `miniagent/client.py`:`extract_text_tool_calls` 清理文本时也去掉 `[TOOL_CALL]` / `[/TOOL_CALL]`(原型里解析后会残留空的包装行),加测试。
4. 服务端:`mlx_lm.server --chat-template` 只接受模板文本,而模型目录里的 `chat_template.jinja` 文件可能优先于它,所以更稳妥的做法是为这个适配器建一个单独的模型目录(权重用符号链接,配自己的 `chat_template.jinja`);`scripts/serve_mlx.py` 指向它。训练和服务必须用同一个模板,否则提示词不一致。
5. 新增离线测试:渲染 → 解析 → 与原调用一致,以及"助手回合内无特殊 token"(模型目录缺失时跳过)。
**注意**:基础模型自带的 `<tool_call>` 函数调用能力不再被利用(它本来在这个任务上就是 0/48);数据 v2(原 old_string)和 v3(缩短)都要在新格式下各训练一次才能做那个配对,每次约 105 分钟。

### 新格式(普通文本工具调用)的评测结果(2026-10-26)

**训练**:`adapters/qwen15q4-v5-plain`,v2 数据 + `prompts/chat_template_plain.jinja`,超参同第三次;max-len 4096 内 144 条训练/7 条验证(第三次 152/7),432 步,无发散,训练损失 0.99 → 约 0.35,验证 0.994 → 0.522(第 49 步)。第一次启动后手动停过一次(第 60 步),已原样保留为 `adapters/qwen15q4-v5-plain-stopped-step60`,正式结果来自从头重跑的这一次。
**评测**(dev 48 题,配置 `configs/student-q4-v5-plain-final.json`,其余同基线):**通过 0/48**,基线 4/48(退步 4 题、改进 0 题,McNemar 精确检验 p=0.125,不显著)。失败类别:no_edit 31、max_steps 15、max_tokens 2。
**预测的第一部分成立,第二部分不成立**:(1) "48/48 运行都发出工具调用"成立:48/48,共 623 次调用,平均 13.7 步(基线 333 次、5.9 步;v4 和第 300 步检查点是 0 次)。格式本身的问题确认已解决。(2) "通过数高于 4/48"不成立:0/48。
**为什么没通过**:623 次调用里 bash 598、read_file 24、**edit_file 只有 1 次**(基线 94 次);连续两次完全相同的调用 334 次(54%),典型轨迹是反复跑同一条 `pytest … | tail`,直到步数用完。也就是说模型现在稳定地"会调用工具",但卡在重复探索里,没有走到修改。贪心解码(温度 0)本来就容易陷入重复,基线失败后重复同一条 edit 调用(56/59)也是同一类现象,这里的差别是出现在了更早的探索阶段。
**含义**:(1) 工具调用格式不稳定是真实存在的一层问题,已修好;修好后暴露出下一层:学生在行为层面不会从探索转向修改。(2) 基线 v3 最终的 4/48 依赖的是一个脆弱状态,不应当当作稳定能力来引用。(3) 这些都是单次、温度 0、48 题的结果,不能推出"新格式不如旧格式"——两次训练的数据条数、模板都不同,也没有多次重复。
**没验证的猜测**:训练只用了 144 条(510 条里 70% 因超过 4096 token 被丢弃,留下的偏短、偏简单),可能是行为层面学不会的主因;可行方向是在训练数据里把过长的工具输出截断,让更多样本落进长度限制(不改变轨迹结构,需要检查不破坏 old_string 的可见性)。

### 截断过长工具输出能多留多少训练样本(2026-10-26,只统计,没训练)

对 `data/sft_train_v2.jsonl`(510 条,新格式模板)统计:工具输出共 5092 条,中位数 448 字符、p90 4306、p99 20029;超过 2000 字符的输出占全部工具输出字符的 79%。把每条工具输出截断到 N 字符(保留头尾各一半)后:

| N | 4096 token 内的样本数 | 其中"所有 edit 的 old_string 在前文仍可见" | 全部 508 次 edit 里仍可见 |
|---|---|---|---|
| 不截断 | 151 | **140** | 478(94%) |
| 6000 | 156 | 144 | 378(74%) |
| 4000 | 182 | 155 | 345(68%) |
| 3000 | 220 | **164** | 312(61%) |
| 2000 | 296 | 161 | 251(49%) |
| 1500 | 362 | 159 | 205(40%) |
| 1000 | 418 | 129 | 149(29%) |

**结论**:截断能让更多样本放进 4096 token,但放进去的样本里 old_string 在前文不可见的越来越多(N=2000 时 296 条里只有 161 条可用)。"放得下且所有 edit 都可见"的最大值是 N=3000 时的 164 条,相比不截断的 140 条只多 17%。更糟的是,不可见的样本会教学生"凭空写 old_string",这正是在评测里看到的失败方式。所以朴素截断**不值得做**。另一个不能忽略的问题:推理时工具输出的上限是 20000 字符(`MAX_OUTPUT_CHARS`),训练用更小的上限会造成训练与推理的输入分布不一致,要用就得在代理里同步加同样的上限。
**剩下的可行方向(未验证)**:(a) 更长的序列(受 16 GB 内存限制,需要更大显存的机器);(b) 按步切窗,模仿代理自己的上下文压缩,把长轨迹拆成多条"压缩后的上下文 → 下一步动作"的样本,需要重新设计导出并保证压缩后 old_string 仍可见;(c) 接受 144 条左右的数据量,把训练数据多样性增加(更多种子库、更多任务)而不是更长。
